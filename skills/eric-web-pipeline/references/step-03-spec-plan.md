# Step 3 · 规格与计划 — Spec, Architecture & Task Breakdown

> 中文速览：SDD 的核心一步——把 brief 展开成可执行的 spec：页面清单、组件树、数据模型、交互行为、任务分解。spec 是后续所有 AI 生成代码的对齐基准；代码和 spec 冲突时，先改 spec 再改代码。

## When you're in this step · 判定信号

- 视觉方向与技术栈已冻结，但还没有页面/组件级别的结构；
- 需求涉及多个页面或多个交互流程，脑子里装不下全部细节；
- 大型或模糊任务——按 AGENTS.md 第 11 条，这类工作应进入 plan mode 完成本步。

## Inputs · 进入条件

- `brief.md` + 视觉方向 + 技术选型（Step 1–2 产物）；
- 现有代码库的结构认知（改版时）。

## Action checklist · 行动清单

1. **信息架构（IA）**：
   - [ ] 页面/路由清单：每个页面的 URL、标题、目的、主要 CTA；
   - [ ] 导航结构：主导航、页脚、面包屑、页面间流转；
   - [ ] Path A：列出 section 顺序（hero → 社会证明 → 特性 → … → footer）。
2. **组件清单**：
   - [ ] 每个页面拆成组件，标注复用关系（哪些是全站共享组件）；
   - [ ] 标注每个组件的数据来源（静态文案 / CMS / API / 用户输入）。
3. **数据模型（Path B 必须，其余可选）**：
   - [ ] 实体与字段（ER 草图或表格）、关系、所有权（哪条数据属于哪个用户）；
   - [ ] API 端点清单：方法、路径、请求/响应形状、鉴权要求；
   - [ ] 状态管理边界：服务端状态 vs 客户端状态 vs URL 状态。
4. **交互与状态规格**：
   - [ ] 关键交互流程（注册、下单、提交表单）的正常路径 + 空态 / 加载 / 错误态；
   - [ ] 表单校验规则、权限规则（谁能看什么）。
5. **冻结边界**：明确哪些现有文件/API/设计 token 不许改（frozen surfaces）。
6. **任务分解**：把 spec 切成有序任务列表，每个任务可独立完成和验证；标注依赖关系与可并行的部分。
7. **风险清单**：技术风险（没用过的库）、集成风险（第三方 API）、内容风险（文案未到位）。
8. 用 `templates/spec-template.md` 写出 `spec.md`。

## Decision tables · 决策表

| 项目规模 | spec 深度 |
| --- | --- |
| 单页营销站（Path A） | 半页到一页：section 清单 + 组件 + 文案大纲即可，数据模型跳过 |
| 多页站点 | 完整 IA + 组件清单 + 简化数据模型 |
| Web App（Path B） | 全量：IA + 组件 + 数据模型 + API + 交互状态 + 权限 |
| 3D 体验（Path C） | IA 弱化为"章节/场景清单"，增加性能预算与降级方案条目 |

## Exit criteria · 出口质量门

- [ ] `spec.md` 存在且覆盖：页面清单、组件清单、（Path B）数据模型与 API、关键交互的三态；
- [ ] 任务分解表存在，每个任务有明确的完成判定；
- [ ] 冻结边界已列出；
- [ ] 拿 spec 对照 brief 自查：spec 的每一项都能追溯到 brief 的某条需求，无自发加戏。

## Common pitfalls · 常见坑

- **spec 里发明需求**：brief 没有的功能出现在 spec 里——逐条回溯，多余的删掉；
- **任务切太大**："实现整个后端"不是一个任务；切到一次能写完并验证的粒度；
- **忽略三态**：只写了正常路径，上线后空态/错误态裸奔；
- **spec 写完不维护**：实现中改了设计却不回写 spec——spec 是活文档，随实现更新。

## Route to existing skills · 路由

- `iterate-until-verified` 第 2–3 节（gates 与分解方法）；
- Path B 的数据/认证设计可先翻 `security-review` 的清单，把安全要求写进 spec 而不是事后补。

## Output artifacts · 产出物

- `spec.md`（规格文档）；
- 任务分解表（可并入 spec.md 或 progress 文件）。

## Handoff · 衔接

- spec 完成且任务有序 → **Step 4 Scaffold**；
- 实现中发现 spec 错了 → 回本步改 spec（记录变更），再回去继续写代码；
- 小项目可合并 Step 3–4：一页 spec 写完直接搭骨架。
