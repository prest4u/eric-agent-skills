# Step 10 · 迭代与维护 — Iterate: Feedback, Analytics & Evolution

> 中文速览：上线不是终点——收集反馈与数据，决定下一轮改什么、从哪一步重新进入流程。纪律：迭代也要走流程，小改走快速通道，大改回 Step 1 重立契约；progress 文件持续维护，它是跨 session 的记忆。

## When you're in this step · 判定信号

- 站点已上线（Step 9 完成），进入运营/改进阶段；
- 用户带着"上线了，现在要改/加/优化 X"回来。

## Inputs · 进入条件

- 生产环境运行中的站点 + progress 文件（全步勾选）；
- 反馈来源：用户意见、分析数据、错误监控。

## Action checklist · 行动清单

1. **反馈收集与分类**：
   - [ ] 真实用户反馈、数据分析（流量、转化漏斗、热力图）、错误监控三路汇总；
   - [ ] 分类：bug / 体验问题 / 新需求 / 内容更新；
2. **定级与路由回流程**（见下表）：判断每条改动该从哪一步重新进入；
3. **分析与实验**（有流量后）：
   - [ ] 关键指标基线：访问量、跳出、CTA 转化、Core Web Vitals 真实用户数据（CrUX/RUM）；
   - [ ] 重要改动用 A/B 或前后对比验证，不靠感觉；
4. **内容维护**：文案更新、素材替换、链接有效性定期巡检；
5. **技术维护**：
   - [ ] 依赖定期升级（安全补丁优先，功能升级挑时机）；
   - [ ] 性能回归监控：Lighthouse/RUM 定期复跑，劣化即查；
   - [ ] 备份与数据安全（Path B）：数据库备份策略实测恢复一次；
6. **文档保鲜**：spec.md、README、AGENTS.md、progress 文件与实际状态同步——文档说谎比没文档更糟；
7. **技术债管理**：记录债务清单（quick & dirty 的角落），攒到影响迭代速度时安排专门一轮还。

## Decision tables · 决策表（改动定级 → 重新入口）

| 改动类型 | 例子 | 重新进入 |
| --- | --- | --- |
|  typo/文案/换图 | 改标题、换 hero 图 | 直接 Step 6 → 8 快速验证 → 9 |
| 单组件调整 | 改按钮样式、加一个卡片 | Step 5/7 定点 → 8 受影响项 → 9 |
| 新 section/新页面 | 加博客、加定价页 | Step 3 补 spec → 4-9 |
| 新功能（含数据/权限） | 加评论系统、加支付 | **回 Step 1** 重立契约，走全流程 |
| 视觉重定位 | 换品牌风格 | 回 Step 2 重做方向 → 后续全走 |
| 线上事故 | 白屏、支付失败 | 立即回滚（Step 9 预案）→ 修复 → 重走 8→9 |

## Exit criteria · 出口质量门

- [ ] 每条反馈/改动都已分类并按上表路由；
- [ ] progress 文件反映当前真实状态（含本轮迭代的步骤勾选）；
- [ ] 指标基线已建立或有明确的"暂无流量"标注；
- [ ] 文档与实际一致。

## Common pitfalls · 常见坑

- **热改生产**：绕过流程直接在线上改——任何改动走对应步骤，哪怕很小；
- **progress 文件荒废**：跨 session 后没人知道在哪一步——每轮迭代结束必更新；
- **依赖恐惧症/升级狂热**：两个极端都要不得——安全补丁及时打，大版本挑窗口升；
- **凭感觉迭代**："我觉得用户想要"——先建指标基线，改动看数据。

## Output artifacts · 产出物

- 更新的 progress 文件 + 指标基线记录 + 技术债清单。

## Handoff · 衔接

- 项目稳定运营 → 本步循环；
- 项目目标根本变化（转型、重构）→ 回 **Step 1** 重新开始一轮。
