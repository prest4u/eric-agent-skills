# Consulting Mode · 顾问模式手册

> 中文速览：开工前的规划对话模式。以顾问身份和 Eric 把项目定清楚——用 `grilling` 的设计树方法分轮拷问 → 输出定案（brief + 阶段分解）→ 针对**这个项目的具体答案**预判每个阶段最可能出的问题 → 设定防漂移锚点。Consulting 的产出，就是后续执行期每一步 review 的对照基准。

## 何时进入 · When to enter

- Eric 开新 session 说"帮我规划/定一下这个网站项目"、"consulting"、"开工前聊聊"；
- 新项目还没有 `brief.md`，且 Eric 想先讨论再动手；
- 已有项目要重定向/大改（从 Step 1/2 重进）时的再规划。

顾问模式**不写实现代码**。它止于定案、风险预判与锚点；之后按 10 步 pipeline 正常执行。

与 `grilling` skill 的关系：提问协议遵循 `grilling`（设计树、frontier 分轮、每题附推荐答案、事实自查不烦用户）。若 `grilling` 已被激活，直接在其框架下运行，本题库作为 pipeline 专用设计树。

## 顾问流程 · The 5 phases

### P1 · Intake 收录

1. 记录 Eric 的一句话需求与所有已知约束（预算、时间、受众、已有资产）；
2. **先自查再开口**：现有仓库结构、`package.json`、品牌文件、域名线索——能从环境查到的事实绝不问 Eric（grilling 纪律）；
3. 确定咨询目标：本次 session 要定到什么粒度（通常 = brief 完整 + 阶段分解 + 风险预判）。

### P2 · Grill 定案（分轮拷问）

按下方**题库设计树**工作。规则（复用 grilling）：

- 把全部待定决策建成设计树，每轮只问 **frontier**（前置已定的决策），一轮问完整个 frontier，编号 + 推荐答案，等回答后再算下一轮；
- 依赖本轮未决问题的题留到后轮；能自查的事实先查；
- 问题格式：

```
❓ **Q1** - **<问题标题>**: <问题正文，可含选项>

➡️ <你的推荐答案>
```

- frontier 清空（无沉默假设）后，请 Eric 确认达成共同理解，再进入 P3。

#### 题库设计树（按 pipeline 阶段组织；按 Path A/B/C 分叉取用）

**Round 0 · 定路径（第一问永远是它）**

- Q0-1 交付物类型：营销/作品集站（A）｜Web App（B）｜3D/创意体验（C）？→ 答案决定后续展开哪套分支。

**Step 1 域 · 目标与验收**

- Q1-1 受众是谁？在什么设备、什么场景下访问？
- Q1-2 访问者看完应该做什么动作（唯一主 CTA）？
- Q1-3 验收标准：把"高级/快/专业"翻成 3 条以上可观测条件（给示范：LCP ≤ 2.5s、375px 无横向滚动、表单闭环）？
- Q1-4 本期明确**不做**什么？（边界清单比需求清单更能防漂移）
- Q1-5 截止时间与失败成本：晚了/砸了会怎样？→ 决定流程重量（小项目合并步骤）。

**Step 2 域 · 方向与选型**

- Q2-1 有没有参考站/品牌资料/视觉方向偏好？没有的话，是否接受生成 2–3 个方向供挑？
- Q2-2 技术栈约束：已有项目栈？托管平台偏好？团队熟悉度？
- Q2-3 素材从哪来：真实拍摄 / AI 生成 / 素材站？版权红线？
- （Path B）Q2-4 数据与账号体系：要登录吗？数据归谁？支付必需吗（首期可否跳过）？

**Step 3 域 · 范围与结构**

- Q3-1 页面/功能清单的优先级：哪些是"没有就不算完成"，哪些是"有了更好"？
- （Path B）Q3-2 核心数据实体与权限边界：谁能看什么？
- Q3-3 最大的技术不确定性是什么？要不要先用 PROOF 模式做最小验证？

**Step 9 域 · 交付与上线**（开工前就要问，因为它反推 Step 1–2 约束）

- Q9-1 发布到哪？谁有部署权限？域名有了吗？
- Q9-2 面向国内访问？→ ICP 备案是否已办（未办是硬阻塞，直接影响选型）？
- Q9-3 预算与额度约束（托管费用、API 费用、Kimi 额度档位）？
- Q9-4 上线后谁维护？有没有分析/监控要求？

**Step 5–8 域**的问题不前置问 Eric——由 P4 风险预判覆盖，执行时按各 step 文件自查。

### P3 · 定案输出

用既定模板落地三份文件（新项目则在项目根目录创建）：

1. `brief.md`（`templates/brief-template.md`）——拷问答案的固化；
2. `spec.md` 骨架（`templates/spec-template.md`）——阶段分解：至少填好 IA 页面清单与任务分解表，细节允许在执行到 Step 3 时补全；
3. `web-dev-progress.md`（`templates/progress-tracker.md`）——勾选状态 + 写入锚点（见 P5）。

### P4 · 逐阶段风险预判（项目特定，不是通用清单）

**推导方法**：遍历 P2 的每个答案，把其中的**约束、缺口、不确定性、冲突**映射到它会在 pipeline 哪一步爆雷。每条预判三要素：问题 + 触发信号 + 预防动作。

映射示例（演示推导逻辑，实战按真实答案推导）：

| Eric 的答案 | 爆雷阶段 | 预判 |
| --- | --- | --- |
| "素材后补，先做起来" | Step 6 | 文案/图片阻塞交付 → 预防：Step 5 就用主题相关草稿并标注待替换 |
| "预算有限" | Step 2 | 选型超配（选了收费服务）→ 预防：选型先过成本表 |
| "面向国内用户" | Step 9 | ICP 备案未办无法上线 → 预防：Step 1 验收标准写入备案前置 |
| "我想要那种很炫的效果" | Step 7 | 动效堆料失控、帧率崩 → 预防：Step 2 定方向词时明确动效预算 |
| "可能要加会员功能，以后再说" | Step 3/5 | 架构没留扩展位，二期推倒 → 预防：数据模型预留、冻结边界写明"预留不实现" |
| "先发给我看看再上线" | Step 9 | 发布授权链不清 → 预防：写明 staging 预览 → 确认 → 发布的顺序 |

输出格式（每个阶段 2–4 条，没有就写"无显著预判"）：

```markdown
### Step N · <阶段名> — 本项目风险预判
| # | 最可能出的问题 | 触发信号（如何提前发现） | 预防动作 |
```

### P5 · 锚点设定（防漂移核心）

把以下 4 类锚点**写死**在 `web-dev-progress.md` 的锚点区：

1. **验收标准原文**（来自 brief，逐条照抄，不改写）；
2. **冻结边界**（本期不做清单 + 不许动的现有文件/API/token）；
3. **视觉方向词**（Step 2 定的那一个词 + 参考）；
4. **路径变体**（A/B/C 及理由）。

规则：锚点**不得静默修改**。任何步骤中想动锚点，必须走显式变更（记录日期/原因/新旧值，见下方纠偏协议）。

## 阶段 Review 协议 · Per-stage review

每个 step 出口（勾进度之前）做一次 5 分钟审查，三问：

1. **达标**：该步 exit criteria 逐条过了吗？证据在哪？
2. **对齐**：本步产出对照锚点有偏差吗？（验收标准有没有被悄悄放宽？方向词有没有变味？边界有没有被踩？）
3. **应验**：P4 对本步的风险预判出现了吗？出现了就记录处置；没出现就标注"未应验"。

结论三选一写入 progress 文件的 Review 记录：`pass` / `偏差-已纠` / `回退到 Step X`。Eric 随时可以说"review 一下当前阶段"——立刻按此三问执行。

## 漂移检测与纠偏 · Drift detection

**漂移信号**（执行期任何一步发现以下任一情况，立即停下）：

- spec 或代码里出现了 brief 没有、也无法回溯的需求（范围膨胀）；
- 技术栈/依赖被换掉但 progress 锚点区没有变更记录；
- 视觉方向悄悄偏移（做了和方向词相反的选择，如"极简"项目里出现多层渐变动画）；
- 验收标准被暗中放宽（"这个指标先不卡了"）；
- progress 文件与实际状态不符（步骤被跳过未记录）。

**纠偏协议**：

1. 停下当前工作，向 Eric 明示漂移点（证据：哪个产物 vs 哪个锚点）；
2. 二选一：**改锚点**（需求真变了 → 显式记录变更，必要时回 Step 1/2 重立）或**回锚点**（实现跑偏了 → 把产物改回锚点方向）；
3. 记录进 progress 文件的漂移检查记录表；
4. 继续。

## 咨询报告模板 · Consulting session 最终产出

一次 consulting session 结束时，交付（文件 + 聊天摘要同构）：

```markdown
# 项目咨询报告 · <项目名> <日期>

## 定案（来自 Grill）
- 交付物/路径：…  受众与 CTA：…  验收标准：…  不做清单：…
- 技术栈：…  素材策略：…  发布与预算：…

## 阶段分解
- 10 步中本项目实际走的路径（含合并/跳过及理由）；任务分解表位置

## 逐阶段风险预判（项目特定）
- 每阶段 2–4 条：问题 / 触发信号 / 预防动作

## 锚点（防漂移）
- 验收标准原文 / 冻结边界 / 视觉方向词 / 路径变体

## 已落盘文件
- brief.md / spec.md（骨架）/ web-dev-progress.md（含锚点与首轮 Review 记录）
```

## Anti-patterns · 顾问模式反模式

- 把题库当问卷一次倒给 Eric——必须分轮、只问 frontier、给推荐答案；
- 问能自己查到的事实（grilling 纪律）；
- 风险预判写成通用清单（"注意性能""注意安全"）——每条必须来自这个项目的具体答案；
- 定案未经 Eric 确认就开写代码；
- 锚点设了之后执行期从不回看——锚点的价值全在 checkpoint 对照。
