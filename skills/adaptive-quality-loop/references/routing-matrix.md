# Choose evidence for the result

Use only the row relevant to the actual acceptance criteria. Evidence can come from native tools; another Skill is never a prerequisite.

| Result | Useful evidence |
|---|---|
| Code or UI | Targeted behavioral checks; build/types where affected; actual runtime for interactions |
| Data or analysis | Source date and provenance, necessary data-quality checks, recomputed key claims and stated limits |
| PDF, document, or slides | Current rendered pages for layout plus checks for the content actually changed |
| Video | Relevant playback, frames, audio, timing, and delivery metadata |
| Skill or configuration | Effective settings, trigger boundaries, consistency of reachable instructions, and affected executable contracts |
| Formal external action | Exact target, existing authority, recovery, current required evidence, independent review, and authorized post-action verification |

Use a specialist only for a concrete unresolved question that needs it. Do not stack source, renderer, reviewer, and release workflows merely because all are available. Reuse trustworthy current evidence across roles.

Create a reusable validator only for a recurring failure or a required repeatable release boundary. Do not build a framework for one reversible edit.
